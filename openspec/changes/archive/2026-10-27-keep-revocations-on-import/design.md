## Context

Причина инцидента — `proposal.md`, раздел Why. Импорт живёт в слое приложения: `parseConfigFile` (`src/app/config-file.ts`) проверяет файл целиком, `importJson` (`src/app/index.ts`) заменяет конфигурацию. Отзыв — поле `revokedAt` (`docs/adr/0001-time-representation.md`, решение 3; `openspec/specs/early-revoke/spec.md`). Ограничения: СБ, п. 2 (файл проверяется целиком до изменения данных) и СБ, п. 3 (операция меняет только то, что выбрал человек).

## Goals / Non-Goals

**Goals:**
- Цепочка «выдать, экспортировать, отозвать, загрузить тот же файл» оставляет доступ закрытым без действий человека.
- Человек видит, что с его файлом что-то сделано.

**Non-Goals:**
- Предпросмотр импорта (следующий запрос заказчика, `import-preview`).
- Слияние выдач и удалений, сделанных после экспорта.

## Decisions

1. **Одна запись — совпадают идентификатор, субъект, сервис, начало и окончание.**
   Отвергнутая альтернатива: только идентификатор. Идентификаторы переиспользуются: `nextPermissionId` в `src/app/permissions.ts` берёт `p<число записей + 1>`, и после удаления новая выдача может получить старый `id`. Совпадение по одному `id` перенесло бы отзыв на чужое разрешение.
   Отвергнутая альтернатива: субъект + сервис без `id`. У одного субъекта бывает несколько временных разрешений на сервис (`early-revoke`, сценарий «Два прямых временных»), и отзыв перескочил бы на соседнее.

2. **При расхождении побеждает отзыв: остаётся более ранний из двух моментов отзыва, остальное — из файла.** Открытый доступ там, где его сознательно закрыли, дороже закрытого там, где хотели открыть: первое заказчица заметила только ручной проверкой перед согласованием, второе видно сразу по ответу «Доступа нет» и исправляется удалением записи и новой выдачей.
   Отвергнутая альтернатива: файл побеждает всегда (поведение до изменения) — это и есть инцидент.
   Отвергнутая альтернатива: отвергать файл, который «откатывает» отзыв, с ошибкой. Марина грузит файл, чтобы вернуть другие правки; отказ заставил бы её править JSON руками.
   Отвергнутая альтернатива: спрашивать человека в момент загрузки. Требование шага — без каких-либо действий человека; вопрос перед применением появится в `import-preview`.

3. **Слияние — чистая функция `mergeImport(current, incoming)` в новом `src/app/import-merge.ts`,** возвращает `{ config, keptRevocations }`. `importJson` вызывает её только после успешного `parseConfigFile`, поэтому файл с ошибкой по-прежнему не меняет ни конфигурацию, ни сохранённую копию (СБ, п. 2).
   Альтернатива: класть логику в `parseConfigFile`. Отвергнута: разбор файла не должен зависеть от текущего состояния, он же читает сохранённую копию в `storage.ts`.

4. **Наблюдаемость: `import-status` дополняется строкой «Сохранён отзыв: p6».** `ImportResult` получает поле `keptRevocations`. Человек видит, что файл применён не буквально, и по какой записи.

5. **Известные ограничения записаны в спеке** (`openspec/changes/keep-revocations-on-import/specs/config-import/spec.md`): запись с тем же `id` и другим содержимым берётся из файла; удалённые после экспорта разрешения возвращаются, выданные после экспорта пропадают. Их закроет предпросмотр импорта, где человек увидит эти различия до применения.

6. **Порядок реализации.** Первым остаётся красный тест инцидента `src/components/RevokeAndImport.test.tsx`; затем тесты `mergeImport` на каждое решение; затем реализация.

## Risks / Trade-offs

- [Человек хотел файлом «вернуть» отозванное разрешение] → отзыв не отменяется импортом; чтобы вернуть доступ, нужна новая выдача. Риск принят: так же работает отзыв на экране (отмены нет, `early-revoke`).
- [Файл с отредактированным руками интервалом у той же записи] → запись считается другой, отзыв не переносится; ограничение записано в спеке и будет видно в предпросмотре.
- [Ранний отзыв в файле закрывает доступ раньше, чем на экране] → это направление «закрыть», оно безопасно; сценарий в спеке.
